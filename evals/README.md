# Evals

Two evals score the reader and the filing worker on a synthetic set, and one smoke run checks
them in CI without any model.

- The **reading eval** reads every document of a split the way the app does (`read_document`
  in development mode), then runs the filing rules (`decide`) on the reading. Nothing is filed.
- The **filing eval** replays those recorded readings through the real worker, filer and secrets
  gate on a temporary vault, and checks what ended up where.
- The **smoke run** does both on about two dozen `val` documents, from recordings committed in
  this repo, and fails when a number is below its threshold.

## The set and the splits

`evals/datasets/eval-v1` is generated by `synth/` (seed 7). Its documents are fictional; every ID
page carries a `SPECIMEN` line, Aadhaar-style numbers fail the Verhoeff check and card numbers
are the networks' published test numbers. Each **base** (one fictional document, such as
`health_policy-1`) comes as up to four **variants**: a `clean` PDF, a `photo`, a `scan` and, for
insurance papers and card statements, a `locked` PDF. Whole bases go to one split: base numbers
divisible by 5 are `test`, those with remainder 1 are `val`, the rest are `train`.

Prompts, cues and thresholds are tuned on `val` only. The `test` split is scored once, at the end
of M2, and that run is the committed baseline.

## The search set

`evals/datasets/search-v1` scores search (M3) on a synthetic vault. Build it with
`make search-set`; the files are deterministic and a test rebuilds them byte for byte.

**The vault of a split** holds the split's eval-v1 documents in the photo variant (a card with
a back lists both files, as the filing eval drops them) and the same split of two extra sets,
`search-x1` (seed 11) and `search-x2` (seed 12). The extra sets use eval-v1's per-type counts,
the clean variant only, and outsider, unclear-name and missing-field rates of 0, so each of
their documents files. That makes a vault about three times the eval-v1 documents. The eval-v1
ones are filed from their recorded readings, so questions about them measure reading and search
together; the extra ones are filed from oracle readings, so those measure search alone. Results
report the two origins apart. Only the extra sets' `val` and `test` documents are committed
(`extra/`).

**Only filed documents are asked about.** An eval-v1 document whose truth expects a question
(an outsider, unclear initials, a missing required field) is in the vault, but no question
targets it and no list expects it. `summary.json` counts them as `documents_left_out`.

**Question kinds** (about 210 a split, in `val.jsonl` and `test.jsonl`):

- **lookup** (100): one value of one document: an identifier, a date, an amount or who issued
  it. `field` is always a stored field and `value` its stored value; `page` and `box` are the
  truth line that prints it. A "still valid" or "still under warranty" question names the real
  field the status comes from and adds `status`: for a validity question `field` is the type's
  expiry-role field and `status` is `{"valid": true or false}`; for a warranty question `field`
  is `warranty_parts` and `status` maps each part's name to whether its cover (purchase date
  plus its years) still holds. Both are worked out at `EVAL_TODAY` (20 Nov 2026); `status` is
  null on every other question.
- **find** (50): names a document ("Kavita's PAN card"); one target.
- **list** (40): templates over people, areas, types, date roles, places and date phrases.
  `query` is what `resolve` returns for a perfect reading at `EVAL_TODAY`; `expected` is
  recomputed from truth fields by `apply_query` (people match the owner or a linked person; areas
  expand to types; the range applies to the role's date field; a place is a contained phrase of
  the type's place field).
- **none** (20): a type, a product or a person the vault does not hold.

`targets` is every filed document that fits the words the prompt uses: the type noun counts for
every type whose label holds it ("card" is also a card statement, an Aadhaar card and a warranty
card; "certificate" is a dozen types), plus the person, place, brand and product it names. The
generator adds a constraint until every target holds the same `value` (and `status`), and drops
the question when it cannot.

**Styles:** `question` (a full sentence), `terse` (a few words), `typo` (one wrong letter in a
word that is not a name, place or brand) and `synonym` (fridge, TV, car, mobile, mediclaim for
the plain term). `origin` is `eval-v1` when any target or expected document is eval-v1.

Search tuning uses `val` only; `test` is run once, at the end of M3.

## Metrics

Per document, the reading eval records booleans and numbers, never a field value or raw model
output.

- **Type accuracy**: the share of documents whose top type equals the truth.
- **Person accuracy**: over documents whose rule is not `home`, the share where the owner is
  right. Where the page names an outsider or an unclear name, the app is right only when it asked
  `person_unknown` or `person_unsure`.
- **Linked people**: right when the people linked to the document, leaving out the owner, are the
  truth's. The owner is never listed as linked, in the record or in the people table.
- **Fields exactly right**: the share of truth fields that are not `None` that were got right,
  overall, by variant and per type, and per field. A date is right by value, an amount by number,
  a list as a multiset of its item keys, other text by the normaliser of its kind. A document read
  as the wrong type scores every truth field as wrong and adds no false positives. Secret fields
  (card number, CVV) are scored from `Reading.secret_values` and never written out.
- **F1**: from `tp` (right), `fp` (a value where the page prints none, or a wrong value) and `fn`
  (a printed field that was missed or wrong), pooled over all documents, per type
  (`field_f1_by_type`) and per field (`field_f1_by_field`, keyed `<type>.<field>`). Each document
  records its `[tp, fp, fn]` per field, and they add up to the document's own `tp`, `fp` and `fn`.
- **Line recall**: the mean over photo pages of `score_page` over the page's English lines. It is
  taken from the pages as the page reader returned them.
- **Silent misfile**: a document the app would file (`outcome == "file"`) to an owner or folder
  other than the truth's. Reported as a count and per 100 documents.
- **`Needs a look` share**: the share of documents the app would ask about, two ways: over
  documents whose `expected_ask` is empty (the target is 0) and over all documents.
- **Seconds**: the median and the maximum per photo, from the recording's own timings.

The filing eval adds, from the real worker:

- **Placement equals the decision**: of the documents the reading eval would file, the share
  filed to that owner and folder. Must be all.
- **Exact copies caught**: a copy of a file (`<name> (1).<ext>`) is caught when the content ends
  filed once and every other file with the same content is held as a duplicate. Must be all.
- **Wrong merges**: documents held as a duplicate or a possible copy though no copy of them was
  dropped. Each vault holds one variant of each base, so any such hold is against a different
  document. Must be 0.
- **Secrets found**: `scan_outputs` over the vault, the database and the logs, with every card
  number of the split, every PDF password and the master password as known secrets. Must find 0.
  An untouched original that still waits on a question in `Inbox` is skipped and counted under
  `waiting_originals_skipped`. Only that item's own path counts, and only while its bytes still
  match; photos are counted only if the scan reads them, which it does not.
  **Values stored for cvv**: rows and record files with a value for `cvv`. Must be 0.
- **Undo then retry**: three filed documents of the clean vault are undone and retried; they must
  come back to the same path.
- **Files left in Inbox**: files that are neither held nor a card asked about in place. Must be 0.

## Search metrics

`python -m evals.runner search` builds a vault of a split (the eval-v1 documents in the photo
variant replayed from their recorded readings through the real worker and filer, a card with a
back uploaded as the filing eval does, then the extra documents from oracle recordings), asks
every `search-v1` question of the split, and scores what the app returns. "Today" is 20 Nov 2026
(`EVAL_TODAY`). Each question runs twice: the quick search (keywords and vectors, no prompt
reading) and the full search as the route runs it (read the prompt, resolve it, list or look
up, compose the answer or the sentence); each is timed. Every metric is also split by `origin`
(`eval-v1`, `extra`) and the summary carries the number of questions behind each rate under `n`.
A rate over no questions is null.

- **top1**, **top3**: over lookups and finds, a target is the first row, or among the first
  three rows, of the full search. **quick_top3** is the same for the quick search.
- **answer_correct**: over lookups, the answer's field is the question's field and its value
  equals the truth after normalising by the field's kind (dates and amounts by value, a list as
  a multiset of items, text as the reading eval does). For a status question the status the
  answer text states must also equal the question's `status`. A decline, or a prompt read as
  anything but a lookup, counts as wrong.
- **citation_accuracy**: over the answers given, the answer's document is one of the targets and
  one of its cited lines is on the truth page and overlaps the truth box with IoU 0.5 or more.
- **list_reading**: over lists, the resolved `Query` equals the truth on intent, people, types
  after area expansion (types plus the types of the areas), role, range and place.
- **list_precision**, **list_recall**: over lists, the rows of the full search against `expected`,
  averaged over the questions.
- **declined_when_none**: over none questions, the share the app declines. **declined_when_answerable**:
  over lookups and finds, the share it declines (lower is better). A question is declined when
  the lookup answer is a "No direct answer", a person in the prompt is not in the household, no
  row comes back, or the top row has no filter behind it and thin evidence (the weak-match rule
  of `compose`: fused score under `MIN_FUSED` and fewer than `MIN_KEYWORD` matching lines).
  Both metrics follow the weak-match rule as it stands (`weak_match`, shared with the app), so
  results from before that rule changed are not comparable.
- **seconds_quick**, **seconds_full**: the median and 95th percentile of the wall time of each
  search, with the first question left out and reported as `cold_first_seconds` (the model
  loading). They mean something only on a live run with the Mac otherwise idle; on a replay
  they are the cost of the code alone.
- **backstop_conflicts**: the number of slots where the words of the prompt (a household name, a
  date phrase, a document type word) and the reading model disagreed. The model's slot is kept;
  code fills only a slot the model left empty or wrote in words it could not read.
- **secrets_found**: `scan_outputs` over the vault, the database (the search tables included)
  and the logs after the run. Must be 0.
- **readings_missing**: prompts whose reading was off or not recorded. **vectors_missing**: query
  vectors that were not recorded (search then falls back to keywords). Both must be 0 on a replay.

The rows hold booleans, numbers and the question's own synthetic prompt, and a `cause` for each
miss: `reading misread` (the prompt read as another intent or field), `retrieval miss` (the
target was not the top row, or a list's rows are not the expected ones), `weak match declined`,
`field not on the type`, `no located line`, `list slot wrong` (with the slots under `slots`),
`wrong value`, `reading off` and, for a none question, `not declined`.

Prompt readings and vectors are recorded like the readings: `RecordedPromptReader` keys a
reading by the SHA-256 of the prompt (and stores the hash of the reading prompt, so a changed
prompt needs a new recording), `RecordedEmbedder` keys a float16 vector by the SHA-256 of the
text (a query's key includes the model's task line). Each recordings folder holds a
`manifest.json` with the name and digest of the reading model and the embedding model that made
it; a replay refuses a folder made by another model, and `--record` refuses to add to one. `--record DIR` calls the local models and
writes there; `--replay DIR` needs no model.

The smoke part of `make eval-smoke` uses `evals/recordings/search-v1/smoke/`: the 22 smoke
documents as the vault (photos go in first, so a clean copy or a scan of a document already filed
is held as a possible copy), the val lookups and finds whose every target is a smoke photo, and
ten list prompts written for that vault (`questions.jsonl`). Changing the chunking, the reading
prompt or the question set makes these recordings stale: record them again with
`python -m evals.runner search --split val --smoke --recordings evals/recordings/eval-v1/smoke
--record evals/recordings/search-v1/smoke` after deleting the folder.

## How the filing eval is built

Each variant gets its own fresh vault, so the variants of one base never meet and are never
possible copies of each other. In each vault:

- Single files go into `Inbox`. A card with a back is two photos, so it goes in through the
  card upload, as the app takes it. Single-file card photos go in with the secrets store locked,
  then the store is opened and the worker runs again.
- An exact copy of every tenth file that would be filed is dropped: the first with the originals
  (same pass), the next after the worker has finished (later pass), and so on in turn. Card
  photos get no copy, because the filed card is a masked copy, so a second photo of it is not a
  copy of a filed file. The clean vault keeps its first three fileable documents for the Undo step.
- Locked PDFs are unlocked with `vault_synth.sets.locked_password(base_id)`. The truth holds no
  password.

The filer reads a masked card copy again to check the number cannot be read. That copy is made
during the run, so no recording of it exists; the eval's page reader answers a content hash that
belongs to no document of the split with a page that has no lines, a perfectly masked card. How
well the mask covers the number is pinned by the card tests on pixels, not here. A document of
the split with no recording still fails with "no recording".

## Recordings

A recording (`src/household_vault/reading/recorded.py`) holds, for one document keyed by
`document_key` of its files, the pages as the page reader returned them, the raw type answer, the
raw fill answer, the seconds, the engine name and the prompt version. Recordings are written in
development mode only. Before a recording is written, every card-number-shaped run that is not a
published test number is masked, so the eval set's own test numbers survive for scoring and
nothing else does.

- `evals/recordings/eval-v1/smoke/` holds the recordings of the 22 smoke documents from the real
  run on `val` (qwen3-vl:4b and Apple Vision; prompt v3, and v4 for the three lab report files).
  `python -m evals.import_smoke --source <val run folder>` copies them out of a run, finds each
  smoke id by the `doc_id` in the recording, and masks every card- or Aadhaar-shaped number to
  its last four digits. Oracle recordings (the truth read back, built by `evals/recordings.py`)
  still serve the tests that need a perfect run.
- `evals/recordings/eval-v1/test/` is where `make eval` records the real run.
- `var/recordings/val/` is where `make eval-val` records. It is not committed.

## The smoke documents

`evals/datasets/eval-v1/smoke.json` lists the documents; the rule that picks them is in
`evals/recordings.py` (`SMOKE_RULE`, `smoke_selection`) and a test keeps the file equal to it.
All are `val` documents:

- the photo of base 1 of each of the nine hand-drawn types (health_policy, vehicle_policy,
  warranty_card, tax_invoice, aadhaar, pan, card_front, prescription, lab_report) and of
  passport, life_policy, utility_bill, payslip and card_statement;
- the first two locked PDFs, by id, that expect no question;
- the photo of the first card with a back;
- the clean PDFs of the outsider document (prescription) and the missing-field document (pan)
  that the generator guarantees in `val`, and of health_policy;
- the scans of aadhaar and tax_invoice.

## Thresholds

`evals/thresholds.toml` has `[smoke.min]` and `[smoke.max]`. Each rate is the value measured on
the committed smoke recordings less 2 points (the two Needs-a-look shares: plus 2 points); silent
misfiles, wrong merges, secrets, stored CVVs and files left in Inbox are exactly 0. They guard
against regressions and are never tuned on `test`. `[search_smoke.min]` and `[search_smoke.max]`
do the same for the search metrics, with question counts as floors.

## Commands

```
make eval-smoke     # what CI runs: committed recordings, no model, a few seconds
make eval-val       # real models on val, recorded under var/recordings/val (about 2 hours)
make eval           # real models on test, recorded under evals/recordings/eval-v1/test (about 2 hours)
make eval-search-val  # the search eval on val with the local models (needs VAL_RECORDINGS)
make eval-search      # the search eval on test, run once (needs the owner's yes)
```

`make eval` and `make eval-val` call Apple Vision and the local Ollama models. Run them only with
the owner's yes. They write `evals/results/<date>_<kind>_<split>_<commit>.json`, which records
the run (date, machine, OS, Python, commit, whether the code was dirty), the dataset name and the
hash of its manifest, the model tags and digests, the prompt version, the thresholds, the summary
and one row of booleans and numbers per document. A `test` run also rewrites
`evals/results/summary.md` from the newest `test` results, with "Fields exactly right on photos"
first.

The runner's pieces can be run alone:

```
uv run python -m evals.runner reading --split val --engines recorded --record DIR
uv run python -m evals.runner reading --split val --engines mac --record DIR --resume --limit 20
uv run python -m evals.runner filing --split val --recordings DIR
uv run python -m evals.runner smoke --recordings DIR
```

`--resume` replays a document that is already recorded in `DIR` instead of reading it again, so a
run that was stopped can go on where it stopped.
