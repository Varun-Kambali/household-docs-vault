# 0016. A synthetic eval set of 50 document types, scored once on a held-out split
Date: 2026-11-20 · Status: accepted

## Context
The project cannot use real documents: they hold my family's ID numbers, and the repo is public. The M1 spike set (`spike-v0`) had two documents per type, too few to rank close choices. M2 needed a set big enough to tune on without tuning on what it is scored on, with the awkward cases in it on purpose.

## Decision
`eval-v1` is generated by `synth/` from a fixed seed (7). Every document is fictional: ID pages carry a `SPECIMEN` line, Aadhaar-style numbers fail the Verhoeff check, GSTINs fail theirs, other long identifiers fail Luhn, and card numbers are the networks' published test numbers. The licence is CC0 (`evals/datasets/eval-v1/LICENSE.md`).

**Composition.** 50 document types. The 9 most-used types (health policy, vehicle policy, warranty card, tax invoice, Aadhaar, PAN, card front, prescription, lab report) are hand-drawn templates, 10 bases each. The other 41 types are generic form layouts, 5 bases each. A base is one fictional document, such as `health_policy-1`. Each base comes in up to four variants: a clean PDF, a phone photo, a scan, and a locked PDF for insurance papers and card statements. Cards with a back come as two images. The truth for each document holds typed values, absent fields (15% of fields), an outsider named on the page (5%), an ambiguous name (3%) and a missing required field (3%), and the questions the app is expected to ask.

**Splits by base.** Base numbers divisible by 5 are `test`, remainder 1 are `val`, the rest `train`. A base's clean, photo and scan copies always land in the same split, so a document is never tuned on through its twin. `val` and `test` are committed (187 documents each: 59 clean, 59 photo, 59 scan, 10 locked, from 59 bases); `train` is regenerated when M6 needs it. The test split has one base of each form type and two of each hand-drawn type.

**Use.** Prompts, cues and thresholds were tuned on `val` only. The test split was run once, last, on the commit that passed the fresh-clone checks. The one change allowed after it was the spelling snap (0017), measured by replaying the committed test recordings through the new code, with no model call.

**Smoke set.** 22 `val` documents, picked by a fixed rule, with their recordings from the real run committed. `make eval-smoke` replays them through the real reader code, the worker and the filer in CI with no model, and fails if a number drops below a threshold: the value measured on those recordings less 2 points, and exactly 0 for misfiles, wrong merges and secrets. These are regression guards, not targets. `eval-smoke` is a required check on `main`.

**Spike-v0 stays frozen.** The M1 spike results name its documents, so they were left untouched.

## Alternatives considered
- **Use the spike set for M2.** Two documents per type cannot separate a 97% reader from a 94% one.
- **Split by document.** A clean PDF in `val` and its photo in `test` would leak the page's text across the split.
- **Real documents, with only counts published.** Planned for the end of the project (M7), as a check on whether these scores hold. It cannot be the main set.
- **Score both splits on every change.** It tunes the test split by accident.

## Consequences
Numbers are in `evals/results/summary.md`; the test run is `2026-11-20_reading_test_bcfd85d.json` and `_filing_test_bcfd85d.json`, with the re-measure by replay in the `b2a1fde` files.

Limits: the pages are synthetic, so they are cleaner and more regular than real ones. The 41 form types share a generic layout, and the test split holds one base of each, so one odd document moves that type's score a lot (in the live test run four core types sat at 75 to 78% because of one misspelt name each, see 0017). The Kannada lines are correct text but the PDF library cannot shape them, so they say nothing about OCR on Kannada. The phone photos are the clean pages put through a perspective transform, shading and blur in code, not taken with a phone.
